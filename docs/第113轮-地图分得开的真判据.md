## 二、先查：这两条尺子在量什么

| 指标 | 原判据 | 实际量的字段 | 这个字段进画面吗 |
|---|---|---|---|
| `jinAdjPass` | 相邻主线图 `bg.base` 明度差 ≥18 占 ≥80% | `MAP_SCENERY[id].bg.base` | **不进** |
| `decorTypes` | 装饰物类型数 ≥12 | `m.decorScheme`（只有 tree / rock / tuft） | **不进**（主路径读 codex） |

### 2.1 `bg.base` 的消费链（全部 4 处）

1. `skinBg(bg)` —— 只在 guigu 皮下用 `lum > 0.42` 分两档纸色，颜色本身被丢弃。
2. `sc3DarkBase(m)` —— 读 `m.inkBg || m.bg`，**inkBg 优先**。
3. `buildGrass(m)` —— 同上，`m.inkBg` 优先；产出的 96×96 纹理赋给 `grassPat`。
4. 整屏填充 `if (grassPat) {...} else { fill = ...skinBg(m.bg).base }` —— 只要 `grassPat` 在，**这个 else 分支永不执行**。

而 `m.inkBg` 由 `js/xianjie.js` 给全部 171 张图都赋了值（148 张主线 + 23 张支线）。
结论：**spine 上 `bg.base` 的颜色值不进入渲染**，它只在 23 张无 inkBg 的支线图上才铺进地面纹理。

### 2.2 实证：屏幕平均亮度探针

用 `qa/_probe-bgbase.mjs`（一次性探针）在默认鎏金皮下逐图进场，截屏取整屏平均亮度：

| 相邻对 | `bg.base` 明度差 | `inkBg` 明度差 | **屏幕亮度差** |
|---|---|---|---|
| suxing→lingyan | 0.8 | 0.0 | 0.65 |
| lingyan→xiaoping | 1.6 | 0.0 | 0.58 |
| xiaoping→tiangui | **15.7** | 0.0 | **0.77** |
| tiangui→zhenling | **15.3** | 0.0 | **0.30** |
| zhenling→mojie | 17.7 | 15.9 | **12.81** |

`bg.base` 差 15.7，屏幕只差 0.77 —— 等于不显示。而 `inkBg` 差 15.9 时屏幕差 12.81，一眼可辨。
**判据量错了层。**

## 三、顺着这条线，摸出一个真 bug

探针里更扎眼的是中间三行：`suxing / lingyan / xiaoping / tiangui` 的 `inkBg` **全是 `#c5bca8`**，屏幕差 0.3~0.8。四张不同的图，玩家看不出换了地方。

查 `qa/_probe-spine.mjs`，发现 `spine` 上有一整段同档：

```
[#114..#147] linghuan … feiyu  共 34 张  inkBg=#c5bca8
```

**根因**：`js/xianjie.js` 里推进序补丁靠 `next` 链构建 spine，而「前传终点接仙界篇」那行 `xj.next = 'linghuan'` 写在补丁 IIFE **之后**。补丁运行时链在 `xianjie` 处断掉，spine 只有 114 张；剩下 34 张（仙界篇全篇）落进「支线」分支，被统一赋成 `toneOf(ai/numArc, 0)` —— **idx 恒为 0，同篇章内全员同档**。

这个 bug 全程静默：不报错、不缺字段、旧度量还报 98% 达标（因为它复刻的是"设想的算法"，不是跑出来的数据）。

## 四、改法

### 4.1 实现侧（`js/xianjie.js`，三处）

| # | 改动 | 说明 |
|---|---|---|
| 1 | 「前传终点接仙界篇」的 `next` 衔接**移到补丁之前** | 让 spine 构建时链是完整的 148 张 |
| 2 | spine 构建后加**链完整性兜底** | 链长 < 主线图数时按 MAPS 顺序把漏网的补到链尾。宁可顺序粗略，不可静默同档 |
| 3 | 墨阶「相邻必差一档」改为**对结果去重** | 原靠 ripple ±0.5 错开，`u±0.5` 双双落进同一整数区间就撞档（实测 3 对）；改为算完与前一档比对，同档就挪一档，到顶则往下挪 |
| 4 | 金皮补丁目标差 18 → **19**，并加**撞钳位带反向推** | `hexOf` 是 8bit 量化，按 18 推会落到 17.0~17.99（实测 41/147 对卡在这个区间）；暗部段连续多张贴 22 下界，单向往暗推谁都推不动 |

### 4.2 判据侧（`qa/verify-mapscenery.mjs` 重写）

**原则**：闸门只读实现跑出来的数据，**不复刻实现**。

| 新指标 | 判据 | 取代 |
|---|---|---|
| `spineGap` | 主线图全部落在推进链上 = 0 | 新增·链断哨兵 |
| `inkDistinct` | 真实 `m.inkBg.base` 种数 ≥5 | 原模拟值 `guiguDistinctNew` |
| `inkAdjDiff` | 相邻主线图 inkBg 不同 ≥80% | 原 `guiguTierNew(i,N)` 模拟 |
| `inkAdjSame` | 相邻主线图 inkBg **完全相同 = 0** | 新增·直接抓偷懒同档 |
| `jinAdjZero` | bg.base 明度差 = 0 的对数 = 0 | 保留（对 23 张无 inkBg 的图仍有效） |
| `jinAdjPass` | bg.base 明度差 ≥18 ≥80% | 保留（原 P0-3 目标，已能达标） |
| `decorTypes` | **`MAP_CODEX[id].decor` 类型数 ≥12** | 原 `m.decorScheme`（已废弃的粗分类） |

另保留 `legDecorTypes=3` 作参考数据，注明它为何不能当判据。

`decorTypes` 换层后恰好 **12 种**（bamboo / banner / bone / lantern / mist / moss / pine / puddle / rock / ruin / tree / tuft），正好压在目标线上——说明 P1-3 早就实现了，只是尺子一直对着旧字段。

### 4.3 闸门升级

`verify-mapscenery` 从 `metric`（只报数）升为 `gate`（八项全绿才放行）。
理由写在脚本里：上一版"只打印不判定"，让仙界 34 张同色这种真问题连续三轮沉默放行。

**反向验证过闸门有牙**：临时把第二张主线图的 inkBg 改成与第一张相同 → 退出码 1、精确报 `inkAdjSame`，随后立即还原源文件。该验证脚本会改写源文件（有 finally 还原），为避免误跑已在本轮结束后删除；需要复验时按「临时改 `js/xianjie.js` 的 `spine.forEach` 注入一对同档 → 跑 `node qa/verify-mapscenery.mjs` → `git checkout -- js/xianjie.js`」三步走即可。

## 六、经验

1. **闸门不能复刻实现，只能读实现的产物。**
   复刻一份"目标算法"进闸门，等于让尺子跟着设想走：实现没做到位时，尺子照样报绿。
   本轮 `guiguAdjDiff` 报 98% 而真实数据 34 张全同档，就是这个错的标本。

2. **不达标先问"量的是不是玩家看得见的那层"。**
   两条红灯的根因完全不同：金皮那条是**尺子量错层**（`bg.base` 已被 `inkBg` 取代），装饰物那条是**尺子量废弃字段**（`decorScheme` 已被 codex 取代）。
   但金皮那条底下还压着一个真 bug——所以不能一刀切成"改判据"，必须顺藤摸瓜。

3. **"只报数不阻断"等于没有闸门。**
   第110轮把 mapscenery 定成 metric、理由是"度量脚本不阻断回归"。代价是这个真问题活了三轮才被翻出来。本轮升级为 gate 并做了反向验证（注入同档 → 确认报红），闸门才算真的存在。

4. **靠巧合保证的事不算保证。**
   ripple ±0.5 只是"大概率"让相邻错开，撞进同一整数区间就失效。真正稳的做法是算完再去重。

5. **8bit 量化要留余量。**
   目标差 18、按 18 推、量化后落 17.x —— 41/147 对栽在这一步。写"≥N"的约束时，落点目标要取 N 以上一点。
